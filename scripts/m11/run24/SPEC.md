# Run24 — terminal-boundary diagnostic candidate: interface specification (engineering, NOT BOOTED)

Run24 asks one question: **with Run23's proven owned path unchanged (amplifier switches read back
Disable before the endpoint exists, PDR UP, PID1 owns the endpoint and `/dev/msm_audio_ion` under one
two-pair seal, one GPR `GET_SPF_STATE`), when PID1 ends the boot by exiting while still holding BOTH
anchors, does the device reset (and with what reset cause), and what are the effective
`/proc/cmdline` IOMMU options and audio-SMMU IOMMU domain type?** It is a terminal-boundary
diagnostic, not an M11 audio PASS and not CP2: no PCM, no playback, no amplifier enable, no
calibration, no gain, no graph, no DSP memory map, no ION ioctl (no allocation, import, map or
hyp-assign), no persist write. Never-mapped, so the forced init-death is memory-safe. Design:
[docs/m11-run24.md](../../../docs/m11-run24.md) §6.

Differences from Run23 (one causal variable, the terminal, plus the read-only capture):

1. The terminal (the causal variable). On the owned path PID1 never final-closes the anchors and
   never calls `reboot(2)`: after the evidence is sealed and delivered it `_exit(0)`s as PID1 holding
   both anchors (the `RESET_RETAINING_ANCHORS` mechanism). The native terminal core
   (`anchor-native/terminal_core.{c,h}`, byte-faithful to the custodian's ledger/terminal subset) is
   enrolled over both anchors and its decision (`HOLD` for this clean, anchors-held boot) is journaled
   before the deliberate override. Degraded paths (no anchors held) keep Run23's orderly reboot.
2. Read-only capture before the exit: the native cmdline-gate verdict over the full `/proc/cmdline`
   (record `cmdline_gate`: verdict + `iommu.*` values + length; the raw cmdline, which carries the
   serial, is never journaled) and the IOMMU group map (`control iommu_capture` via the spawner,
   record `iommu`).
3. Identity strings `M11R24` / `m11r24`.

## Transport (relay `scripts/m11/run24/kmsg-relay.c`)

Exactly `scripts/m11/run20/kmsg-relay.c` (protocol M11I3, see run20/PROTOCOL.md) with only:

1. Runtime directory `/run/m11-instrumentation/` instead of `/run/m11/` for `logger.stop`,
   `logger.ready`, `usb.ready`, `logger.done`; the event file is
   `/run/m11-instrumentation/journal` instead of `/run/m11/events`.
2. START payload `run=M11R24 nonce=<32 hex>\n`.
3. `EVENT_RESERVE` = 1 MiB + 64 KiB (journal.sh caps the journal at 1 MiB) and `CAP` = 4 MiB
   (K frames keep `CAP - EVENT_RESERVE`).
4. Nothing else: write-only tty (`O_WRONLY`), no host ACK, same SHA seal, same F frame.

The relay runs as uid/gid 65534 without capabilities (spawned by the runtime with
`NO_NEW_PRIVS`); `next/control journal` chowns `/run/m11-instrumentation` and `/dev/kmsg`, and
`run24/usb` chowns `/dev/ttyGS0` before publishing `usb.ready`.

E stream content = the runner journal (`M11I1 <seq> <time> session ...` records, hex payloads,
written by `record()` and `journal.sh`), terminated by `journal_finish`'s
`M11I1 END <seq> <sha256>` line; `logger.stop` holds the journal byte count (journal.sh).

`scripts/m11/run24/{receiver.cs, host-reader.ps1, host-observer.ps1, check-capture.py}` derived

## Runner (`scripts/m11/run24/runner.c`)

`run23/runner.c` (ION node/bind, both anchors, one two-pair seal, census, loan setup, query —
unchanged) plus:

- right after `m11_audio_attach_anchors` and the `anchor` record: `terminal_enroll` —
  `m11_terminal_core_new_boot` + `m11_terminal_core_init(&tc,&boot_ledger,&anchor,&ion_anchor,…)`.
- owned path (PDR UP), after the query: records `spf_query`, `worker_status`, `pd_state` (both
  anchors held, listener registered, ADSP running); **no final close, no retire**. Then
  `cmdline_capture` (record `cmdline_gate`), `iommu_capture` (`spawned(JOB_CONTROL,"iommu_capture")`,
  record `iommu`), `terminal_decided` (`m11_terminal_core_tick` + `m11_terminal_core_action`; record
  `terminal_decision` with the action name and the stated diagnostic override), `evidence_seal`
  (record `pre_transport_teardown`, `control seal`, logger drain), `exit_usb_stop` (`control usb_stop`:
  its 3 s observer grace delivers the F frame before the gadget goes away), `exit_checkpoint`
  (colour), `pid1_exit_forced`, best-effort `m11_spawner_stop`, then `_exit(0)` as PID1 holding both
  anchors (ADSP, mapper and PDR listener still live). The panic after that is not shippable
  (user space stops); the reset cause is read by the post-run oracle.
- degraded paths (endpoint absent, or PDR never UP: no anchor held) keep Run23's orderly teardown
  (`retire` on the PDR-never-UP branch, seal, `usb_stop`, `stop_adsp`, mapper stop, `common`,
  checkpoint, `unmount`, both anchors end `REBOOT`, `reboot(2)`).

Kept from Run23: no host-receipt gate (receive-only observer); PID1 breadcrumbs
`<5>M11R24 pid1 step=<name>` on a fresh `/dev/kmsg` fd before every phase (breadcrumbs after
`evidence_seal` are outside the sealed capture); `control amp_gate` after `usb_start` and before
the spawner; the PID1 fatal-signal hold. Every post-seal job runs through the pre-bind spawner (the
seal refuses `execve`; a PID1 fork would hand both anchor pairs to a child). Colours: green query
READY, red query error, cyan PDR not UP; BLUE from init.

## Post-run oracle (operator, read-only, after Android returns)

`adb shell cat /proc/cmdline` (`bootinfo.pureason=`, `bootinfo.pdreason=`) and
`adb shell cat /sys/bootinfo/powerup_reason`: `0x40001`/`reboot` = orderly reboot,
`0x20001`/`kpanic` = kernel panic, anything else = classify only.

Run24 expectation (the terminal observation): after the owned path's forced PID1 exit the oracle is
expected to read `0x20001`/`kpanic` (init-death panic reset), distinct from Run23's orderly
`0x40001`/`reboot`. A degraded run (no anchors held) reboots orderly and reads `reboot`. Any other
value, download-mode entry instead of a reset, or no return to Android is classified, never retried.
The oracle cannot observe whether `device_shutdown()` ran; that stays source-INFERRED.
